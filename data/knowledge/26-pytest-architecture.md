## pytest Architectural Design

pytest is the de facto standard testing framework for Python. Unlike `unittest` (which was modeled after Java's JUnit and requires boilerplate classes and assertion methods), pytest is designed around idiomatic Python functions, plain `assert` statements, and a powerful dependency injection fixture system.

```
Test Execution Flow in pytest:
  Discovery (test_*.py)
        │
        ▼
  AST Assert Rewriting (Hooking import system)
        │
        ▼
  Fixture Resolution & Dependency Injection (conftest.py)
        │
        ▼
  Hook Engine (pluggy: setup -> call -> teardown)
        │
        ▼
  Reporting & Output Formatting
```

## 1. Automatic Test Discovery

pytest automatically discovers tests across a project directory without requiring manual test suites:
- Searches recursively from the root directory or directories specified on the command line.
- Identifies test files matching `test_*.py` or `*_test.py`.
- Inside those files, collects:
  - Functions prefixed with `test_*`.
  - Methods prefixed with `test_*` inside classes prefixed with `Test*` (note: test classes must NOT have an `__init__` constructor).

## 2. AST Assertion Rewriting

One of pytest's most sophisticated architectural features is **assertion rewriting**:
- In standard Python, `assert a == b` simply raises an `AssertionError` with no detail if the condition is false.
- Instead of requiring cumbersome methods like `self.assertEqual(a, b)` or `self.assertIn(x, y)`, pytest allows developers to use plain Python `assert`.
- **How it works**: When pytest imports a test file, it registers a custom import hook (`_pytest.assertion.rewrite`). It parses the source code into an **Abstract Syntax Tree (AST)**, inspects every `assert` statement, and rewrites the AST to intercept intermediate values before compiling it to bytecode.
- When an assertion fails, pytest prints a rich diagnostic diff showing exact values of sub-expressions, sequence mismatches, and nested dictionary differences.

```python
# You write:
def test_numbers():
    a = 10
    b = 20
    assert a + 5 == b

# Failure output generated by AST rewriting:
#   assert (10 + 5) == 20
#   + where 10 + 5 = 15
```

## 3. Fixtures and Dependency Injection

pytest replaces `setUp()` and `tearDown()` methods with a modular **dependency injection** architecture.

### How Dependency Injection Works:
1. A fixture is defined using the `@pytest.fixture` decorator.
2. When a test function declares an argument whose name matches a fixture, pytest's runner automatically executes the fixture first and injects its return value into the test function.

```python
import pytest

@pytest.fixture
def sample_user():
    return {"id": 1, "username": "alice", "active": True}

def test_user_active(sample_user):
    assert sample_user["active"] is True
```

### Setup and Teardown via `yield`
Fixtures support clean setup and teardown semantics using Python generators:
- Code before the `yield` statement executes **before** the test (setup).
- The yielded value is injected into the test.
- Code after the `yield` statement executes **after** the test finishes (teardown), even if the test fails.

```python
@pytest.fixture
def temp_database():
    db = create_test_database()  # Setup
    yield db                      # Provide fixture value to test
    db.teardown()                 # Cleanup executed guaranteed
```

### Fixture Scopes
Fixtures can be cached across different execution lifecycles using the `scope` parameter:
- **`function`** (default): Executed and destroyed for every single test function.
- **`class`**: Executed once per test class.
- **`module`**: Executed once per test module file.
- **`package`**: Executed once per package directory.
- **`session`**: Executed once across the entire test session run.

### Hierarchical Configuration: `conftest.py`
`conftest.py` files provide global fixtures and configuration hooks across directory trees:
- Fixtures defined in `conftest.py` are automatically available to all tests in the same directory and subdirectories without needing to import them!
- Multiple `conftest.py` files can be nested in subdirectories to override or add fixtures hierarchically.

## 4. Parametrization and Markers

The `@pytest.mark.parametrize` decorator enables data-driven testing by running the same test function against multiple input/output datasets:

```python
@pytest.mark.parametrize("input_val, expected", [
    ("hello", "HELLO"),
    ("Python", "PYTHON"),
    ("123", "123"),
])
def test_uppercase(input_val, expected):
    assert input_val.upper() == expected
```

## Frequently Asked Questions

**Q: How does pytest's test discovery and assert rewriting work?**
pytest discovers tests matching `test_*.py` and `*_test.py` containing `test_*` functions. Through an import hook, it intercepts the AST before bytecode compilation and rewrites plain `assert` statements into introspective reporting code that captures sub-expression values on failure.

**Q: What is the architecture of pytest fixtures?**
pytest fixtures use dependency injection. Test functions declare fixture names as parameters, which pytest matches and resolves at runtime. Fixtures support setup and teardown via `yield` and configurable lifecycles via scopes (`function`, `class`, `module`, `session`).

**Q: What is the purpose of `conftest.py` in pytest?**
`conftest.py` is a root or directory-level configuration file that makes fixtures, hooks, and test helpers universally accessible across test files in its directory tree without requiring explicit import statements.

**Q: Why is pytest preferred over Python's built-in `unittest`?**
pytest eliminates class boilerplate, uses readable plain Python `assert` statements with detailed diff output, provides modular dependency-injected fixtures with clean scoping, and supports rich plugins and concise parametrization.
